## 七、已知问题与解决方案

### 7.1 PyTorch + rclpy 信号处理冲突（Jetson ARM 特有）

**现象**：通过 `ros2 run` 或 launch 的 `Node()` 启动 detector_node 时，在 torchvision 加载阶段报 `corrupted size vs. prev_size` 段错误。直接用 `python3` 运行则正常。

**原因**：rclpy 的 C 层信号处理器在 torchvision 加载 `.so` 动态库（内部调用 malloc）时被触发，破坏了堆内存元数据。这是 ARM aarch64 + NVIDIA 定制 PyTorch wheel + Docker 环境叠加导致的时序冲突，x86 平台不易复现。

**解决**：launch 文件中 detector_node 使用 `ExecuteProcess` 代替 `Node()`，绕过 rclpy 的信号处理器注入。

### 7.2 decision_processor 不被 colcon 自动发现

**现象**：编译成功，目录存在，但 `ros2 pkg list` 找不到。

**原因**：`ament_python` 类型包的 DSV hook 文件缺少 `ament_prefix_path` 条目，colcon 的自动发现脚本未注册该包。

**解决**：在容器 `~/.bashrc` 中手动 export：
```bash
export AMENT_PREFIX_PATH=/ros2_vision_project/ros2_ws/install_docker/decision_processor:$AMENT_PREFIX_PATH
export PYTHONPATH=/ros2_vision_project/ros2_ws/install_docker/decision_processor/lib/python3.10/site-packages:$PYTHONPATH
```

### 7.3 宿主机 setuptools 版本不兼容

**现象**：编译 `vision_msgs_custom` 时报 `canonicalize_version() got an unexpected keyword argument 'strip_trailing_zero'`。

**解决**：
```bash
pip install setuptools==58.2.0 --break-system-packages
```

### 7.4 容器内 GUI 程序无法显示

**现象**：运行 `rqt_image_view` 等 GUI 工具报 `could not connect to display`。

**解决**：宿主机执行 `xhost +local:docker`，容器内设置 `export DISPLAY=:1`（或与宿主机 `echo $DISPLAY` 一致的值）。无显示器的情况下用命令行工具替代。

### 7.5 install_docker 环境变量被污染

**现象**：source install_docker/setup.bash 后 `AMENT_PREFIX_PATH` 中出现宿主机路径（如 `/home/hgzq/...`）。

**解决**：编译前彻底清除环境变量：
```bash
unset AMENT_PREFIX_PATH CMAKE_PREFIX_PATH COLCON_PREFIX_PATH PYTHONPATH
export AMENT_PREFIX_PATH=/opt/ros/humble
source /opt/ros/humble/setup.bash
rm -rf build_docker install_docker
# 然后重新编译
```

## 八、串口设备确认

```bash
# 方法1：插拔前后对比（最可靠）
ls /dev/ttyACM* /dev/ttyUSB* 2>/dev/null   # 拔掉前
ls /dev/ttyACM* /dev/ttyUSB* 2>/dev/null   # 插上后，多出来的就是

# 方法2：查看内核日志
dmesg | tail -20    # 插上后立即运行

# 方法3：查看 USB 设备
lsusb
```

一般规律：STM32 USB 直连 → `/dev/ttyACM0`，USB-TTL 转换器 → `/dev/ttyUSB0`，Jetson 板载串口 → `/dev/ttyTHS1`（推荐）。

### udev 规则（可选，防止设备名变化）

```bash
# 查看设备硬件 ID
udevadm info -a /dev/ttyUSB0 | grep -E 'idVendor|idProduct'

# 创建规则
sudo tee /etc/udev/rules.d/99-stm32-serial.rules << 'EOF'
SUBSYSTEM=="tty", ATTRS{idVendor}=="1a86", ATTRS{idProduct}=="7523", \
  SYMLINK+="stm32_serial", MODE="0666"
EOF

sudo udevadm control --reload-rules
sudo udevadm trigger
```

之后 `protocol.yaml` 中 port 设为 `/dev/stm32_serial` 即可。

五状态状态机 (robot_decision.py)

SEARCHING ──confirmed(连续3帧检测到)──► ALIGNING
   ▲                                       │
   │ TARGET_LOST(连续5帧丢失)              │ |align_angle| > align_thr_deg
   │◄──────────────────────────────────────┤ → 持续turn_angle/turn_wheels
   │                                        │
   │                                        │ |align_angle| <= align_thr_deg
   │                                        ▼
   │                                     MOVING ──TARGET_LOST──► (回SEARCHING)
   │                                        │
   │                                        │ distance <= stop_dist
   │                                        ▼
   │                                     ARRIVED (settle ARRIVAL_SETTLE_S 秒)
   │                                        │ pause_at_arrived=False 且 settle完成
   │                                        ▼
   └─────PICK_DONE(pick_elapsed>=pick_duration)── PICKING (执行pickup_action, arm_distance)
         若 pick_count >= WUGUAN_TOTAL_WEAPONS → all_picked=True → ALL_DONE

各状态输出的 cmd_dict 字段：

search_rotate: SEARCHING时原地旋转搜索
turn_angle/turn_wheels: ALIGNING阶段对齐转向量
forward_dist/drive_wheels: MOVING阶段前进量
pickup_action/arm_distance: PICKING阶段抓取动作与机械臂目标距离


/serial/meilin_cmd 的作用
梅林（树林）阶段的爬升/下降控制指令，由 processor_node._publish_meilin_cmd() 在收到 /meilin/nav_state（来自梅林导航模块）时发布：

字段	含义
linear.x	下一目标台阶编号
linear.y	爬升模式（0=无, 1/2=爬升, 3/4=下降）
linear.z	当前俯仰角
angular.x	与下一台阶的高度差
angular.y	绕道标志（当前固定为0，未启用）
真实硬件：经 auto_serial_bridge 转成 MeilinCmd(0x04) 帧发给 STM32，STM32 据此控制履带/抬升机构完成实际爬坡动作。
仿真：mock_feedback_node.py 订阅它，根据 next_block+climb_mode 把机器人瞬移到对应台阶坐标和高度，模拟爬坡结果。
简单说：它是"上/下第几号台阶、爬升还是下降"的指令，驱动机器人在梅林区跨越方块。

USB摄像头走的是Linux的V4L2(/dev/videoN)子系统，和下位机走的UART(/dev/ttyUSBx，由auto_serial_bridge处理)是两套完全独立的内核驱动/总线，互不干扰，接在不同USB口反而是更好的做法（避免和D435I争抢USB3带宽，Orin Nano Super的USB3通道本身有限）。

但有两个实际问题需要在真机上确认/处理：

/dev/videoN编号会变：D435I一接上会自己占用好几个/dev/video*节点（彩色/深度/红外各一个），加上这个独立精对齐相机，实际编号在Jetson上很可能不是代码里默认的cam_index=4。需要用v4l2-ctl --list-devices在Jetson上实测确认对应哪个/dev/videoN，启动时通过launch参数传入正确值。

重启/重插后编号可能漂移：建议给精对齐相机做一条udev规则，按USB物理端口路径或VID:PID生成一个固定符号链接（如/dev/usb_align_cam），这样不管D435I先枚举还是它先枚举，路径都不变。
